# Deploy Herbliss

Both services build from the repository root on `main`. Vercel serves the storefront and forwards `/api/*` requests to Render. The browser keeps a same-origin session cookie and sends checkout uploads through the same route. Render handles the API, database and WhatsApp. On Render Free, verification emails go over HTTPS to a protected Vercel function, which sends through your existing Gmail account. Local development still runs on one Next.js server using SMTP directly.

## 1. Create the Render API

In Render, create a **Blueprint** from the GitHub repository and select `render.yaml`. It defines a Node 24 **Free** web service named `herbliss-api` and a health check at `/api/health`. For an existing service, select the Free instance in its dashboard as well. [Render Blueprint reference](https://render.com/docs/blueprint-spec)

For manual creation, choose **New → Web Service**, connect `NOMANRAHIM77/herbliss`, branch `main`, runtime **Node**, root directory blank, build command `npm ci --include=dev && npm run build`, start command `npm start -- --hostname 0.0.0.0`, instance **Free**, and health check `/api/health`.

Render Free blocks outbound SMTP ports 25, 465 and 587, so Gmail SMTP credentials belong on Vercel for this setup. Free services also sleep after 15 minutes without traffic; the next API request can take about one minute to wake the service. [Render Free limits](https://render.com/docs/free)

| Setting                                                                                | Value                                                                                          |
| -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `NEXT_PUBLIC_APP_URL`                                                                  | The public Vercel storefront HTTPS origin or custom domain. Use the same origin on both hosts. |
| `MONGODB_URI`                                                                          | Atlas URI for the Herbliss database, with the production database user and password.           |
| `JWT_SECRET`                                                                           | Generated by the Blueprint. Keep it stable across deploys.                                     |
| `NODE_VERSION`                                                                         | `24.x` (set by the Blueprint).                                                                 |
| `EMAIL_DELIVERY`                                                                       | `relay` (set by the Blueprint).                                                                |
| `EMAIL_RELAY_SECRET`                                                                   | Generated by the Blueprint. Copy the same value to Vercel.                                     |
| `ENABLE_EMAIL`                                                                         | Start with `false`; change to `true` after Vercel email settings are deployed.                 |
| `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_ACCESS_TOKEN`, optional `WHATSAPP_GRAPH_VERSION` | Unused by the current click-to-chat checkout; these Meta settings can be removed.              |

Leave `BACKEND_URL` blank/absent on Render. For manual creation, generate separate random values for `JWT_SECRET` and `EMAIL_RELAY_SECRET`, each at least 32 characters. You can generate each value locally with `node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"` and paste it directly into hosting settings.

If your Vercel project already exists, its **Settings → Domains** page shows the `*.vercel.app` address to use as `NEXT_PUBLIC_APP_URL`, with `https://` at the start. If it does not exist yet, you can initially use your Render service's actual HTTPS origin while `ENABLE_EMAIL=false`, then replace it with the Vercel storefront origin before enabling signup. Do not enter a GitHub URL, localhost URL, or an unedited example domain for production.

Allow the Render service’s outbound IP ranges in the Atlas project’s network access settings. Use fresh production credentials in the Render dashboard. Copy the deployed service’s HTTPS origin and check `/api/health` returns `{"status":"ok"}`. This health endpoint checks the server process. Validate Atlas access by logging in through the storefront after the next step. [Render outbound IPs](https://render.com/docs/outbound-ip-addresses)

## 2. Create the Vercel storefront

Import the same GitHub repository, use the **Next.js** preset, and leave the root directory at the repository root. Select Node.js 24.x and use a Vercel plan that permits commercial use for the live shop. [Vercel project settings](https://vercel.com/docs/project-configuration/project-settings) · [Vercel fair use guidelines](https://vercel.com/docs/limits/fair-use-guidelines)

| Setting               | Value                                                                                |
| --------------------- | ------------------------------------------------------------------------------------ |
| `NEXT_PUBLIC_APP_URL` | The production storefront origin, such as `https://your-store.vercel.app`.           |
| `BACKEND_URL`         | The Render service origin, such as `https://your-api.onrender.com`.                  |
| `EMAIL_RELAY_SECRET`  | Exactly the same secret as on Render. Server-only; never prefix with `NEXT_PUBLIC_`. |
| `SMTP_HOST`           | `smtp.gmail.com`                                                                     |
| `SMTP_PORT`           | `465`                                                                                |
| `SMTP_USER`           | Your Gmail sender address.                                                           |
| `SMTP_PASS`           | Your Google app password, without spaces.                                            |
| `EMAIL_FROM`          | The same Gmail sender address.                                                       |
| `STORE_CONTACT_EMAIL` | Your monitored reply inbox; the same Gmail address is fine.                          |

Set `NEXT_PUBLIC_APP_URL` and `BACKEND_URL` before the Vercel build. If the storefront domain differs from the origin entered on Render, update Render’s `NEXT_PUBLIC_APP_URL` and redeploy. Authentication and checkout mutations accept the configured storefront origin. Use a separate staging backend and database to test those flows from a preview URL.

Add these variables to Vercel's **Production** environment and redeploy after changes. MongoDB and JWT credentials stay on Render. Vercel's mail function validates just the SMTP settings; it does not need database access. Neither `ENABLE_EMAIL` nor `EMAIL_DELIVERY` is required on Vercel. No purchased domain is needed to send from your Gmail address. Vercel allows SMTP ports 465 and 587 on its Node.js functions. [Vercel SMTP support](https://vercel.com/kb/guide/serverless-functions-and-smtp)

After the Vercel production deployment is ready, set `ENABLE_EMAIL=true` on Render and ensure `NEXT_PUBLIC_APP_URL` points to that exact Vercel production origin. Redeploy Render. The flow is:

`Signup → Render generates code → authenticated HTTPS request to Vercel → Gmail sends code → Render verifies code`

The internal endpoint is `/internal/email-verification`, outside the `/api/*` forwarding rule. It accepts only an authenticated request with one recipient and a six-digit code. The sender, subject and body are fixed. Unauthorized requests never contact Gmail. Use the public production domain so Vercel deployment protection does not intercept Render's request. Do not send traffic to a protected preview deployment for this setup.

Gmail may block automated sign-ins and has sending limits; a failed email leaves signup incomplete and allows the customer to try again. See the [Gmail setup and troubleshooting guide](SMTP_SETUP.md).

## Other optional settings

- `JWT_EXPIRES_IN`: defaults to `7d` on Render.
- `IMAGE_PROVIDER`: defaults to `imagekit`. Existing images use the committed ImageKit asset URLs and local assets; no ImageKit secret is needed on Vercel.
- `IMAGEKIT_PRIVATE_KEY`: keep on Render if using server-side media management. `IMAGEKIT_PUBLIC_KEY` and `IMAGEKIT_URL_ENDPOINT` are also required by validation if `ENABLE_IMAGE_UPLOADS=true`; leave that flag `false` when no upload integration needs it. Checkout receipts are stored with the order in MongoDB.
- `CHECKOUT_WHATSAPP_TEST_NUMBER`: optional recipient for local development only. Production always uses the store's configured WhatsApp recipient.
- `CRON_SECRET` and the merchant gateway variables are reserved for future features and can remain absent.

## 3. Verify from the storefront

- Open the storefront and check that the product images and videos load.
- Open `/api/health` on the storefront to verify the Vercel rewrite reaches Render.
- Create a test customer, verify the email code, open the profile, then log out and log in again.
- Submit a COD test order, then an Easypaisa test order with a fictional JPG or PNG screenshot. Verify the amounts and screenshot in the receiving WhatsApp inbox after the customer taps Send in WhatsApp.

The storefront currently asks search engines to skip indexing. Email signup requires its provider settings. WhatsApp checkout uses click-to-chat and requires the customer to tap Send; no Meta provider settings are needed.

If signup cannot send a code, confirm both relay secrets match, the Vercel SMTP settings are complete, and the production storefront domain is reachable publicly. A Render `/api/health` success confirms only the running process; it does not verify MongoDB, Gmail or WhatsApp. Final email delivery must be checked through a real signup after configuring both hosts.
